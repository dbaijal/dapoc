# Governance & Template Enforcement — DA vs JCR (xWalk) Comparison

---

## Use Case: Governance & Template Enforcement

How content governance, template policies, and authoring guardrails are enforced to maintain content consistency and quality across the site.

---

| Dimension | Details |
|---|---|
| **Current TFS State** | AEM 6.4 Editable Templates with full policy system. Template policies restrict which components are allowed per template, which RTE options are available, which styles can be applied, and which content structures are locked. Authors cannot add components that are not permitted by the template policy. Governance is system-enforced at authoring time. |
| **DA Approach** | Governance is **process-based**, not system-enforced. DA does not have editable templates or policy-level restrictions. Authors can place any block on any page — there is no mechanism to restrict which blocks appear on which page types at authoring time. Template concept exists only as a metadata value (for styling/code) — not as enforcement. Governance is achieved through: DA permissions (who can edit which paths), Request Publish workflow (reviewers reject non-conforming content before publish), block library (shows available blocks — but does not restrict per page type), and team process/guidelines. |
| **JCR Approach (AEMaaCS + xWalk)** | Provides **moderate guardrails** via component-definition.json and component-filters.json — but does NOT have full AEM Editable Template policies. Component-filters restrict which child blocks can go inside a container (e.g. only accordion-item inside accordion). Model definitions control which properties appear in the UE dialog per block. Section filters can restrict which blocks are allowed in a section. Style options are limited per block via the model's `classes` field. However — there is no equivalent of template policies that restrict which blocks can be placed on a specific page type, no locked page regions, and no per-template content policies for RTE options. |
| **Functional Differences** | Neither DA nor xWalk provides traditional AEM Editable Template + Policy enforcement. Both represent a governance simplification from AEM Sites. DA has no authoring-time restrictions — governance is entirely via review process. xWalk has more guardrails than DA (component-filters, model field restrictions, section filters) but still far less than AEM's full policy system. In AEM 6.4, authors physically cannot add a disallowed component. In xWalk, filters limit options in specific containers but don't control page-level block placement. In DA, authors have full freedom — governance is at publish approval gate. |
| **Operational Impact** | **DA:** Authors have full freedom to author any block on any page. Regional teams have the same open authoring model. Governance overhead shifts to reviewers/approvers who must validate content conformance during the publish workflow. Publishing is gated by approval — non-conforming content is rejected. No additional maintenance of template policies needed — but review effort increases. **xWalk:** Authors see limited options in UE dialogs based on component-filters and models. Slightly more constrained authoring experience reduces reviewer burden. But maintaining component-definitions, filters, and models across 140+ sites adds development maintenance overhead. |
| **Governance Impact** | **DA:** Approval process becomes the primary governance enforcement point. Rollout coordination relies on folder structure and permissions — not template policies. No system-enforced validation or guardrails at authoring time. Governance enforcement depends on reviewer discipline and clear authoring guidelines documentation. Operational controls are permissions-based (who can edit where) and workflow-based (who approves before publish). **xWalk:** Component-filters and section-filters provide some system-enforced governance at the container level. Model definitions ensure only defined properties are authorable per block. However, page-level governance (which blocks on which page type) is not enforced by the system. Governance is stronger than DA but weaker than AEM Editable Templates. |
| **Change Mgmt Impact** | **DA:** Significant shift from policy-enforced governance to process-based governance. Authors accustomed to "I can't add this here" (template restrictions) must adapt to "I can add anything — but it will be reviewed before publish." Training needed on: what blocks belong on which page types (guidelines), the approval process as the quality gate, and the responsibility shift from system-enforcement to human review. Process documentation and authoring guides become critical. **xWalk:** Moderate shift. Authors still see dialogs with limited options (similar to AEM). Training focused on new UE interface and different (simpler) restriction model. Less organizational impact than DA since some system-enforced guardrails remain. |
| **Risks/Limitations** | **DA:** Risk of content inconsistency if reviewers miss non-conforming content. No automated validation before publish (unless custom built). At 140+ sites scale, relying solely on human review for governance may not scale without clear guidelines and disciplined review. No Live Copy overview-style tool to visualise template conformance across sites. **xWalk:** Component-filters only restrict container children — not page-level block placement. No full template policy equivalent. Custom service from 6.4 template policies has no direct replacement. Organizations expecting AEM-level template governance will find xWalk's model simpler but less restrictive. |
| **Notes** | EDS (both DA and xWalk) fundamentally shifts the governance model from "prevent at authoring time" to "validate at publish time." This is by design — EDS prioritises authoring speed and simplicity over restrictive governance. For TFS, the publish approval workflow becomes the critical governance enforcement point in both approaches. The key question is whether TFS's governance needs can be met through approval-based review or whether system-enforced restrictions are a hard requirement. If system-enforced restrictions at the page-template level are non-negotiable, neither DA nor xWalk fully satisfies this today — but xWalk provides more guardrails than DA. |

## Detailed Comparison: Governance Mechanisms

| Governance Aspect | AEM 6.4 (Current TFS) | DA | xWalk (JCR) |
|---|---|---|---|
| Allowed blocks per page template | Template policies — system-enforced | No — any block on any page | Partial — component-filters restrict children inside containers, but not which blocks can be placed on a page |
| Locked page structure (fixed regions) | Editable Template locked regions | No | No |
| RTE formatting restrictions per template | Content policies restrict formatting options | No | No |
| Style restrictions per template | Template policies control which styles appear | No | Partial — model `classes` field limits style options per block |
| Block property restrictions | Policies hide/show dialog fields per template | No | Yes — component-definition controls which fields appear per block |
| Section-level block restrictions | Parsys policies restrict allowed components per region | No | Yes — section filters restrict which blocks are allowed in a section |
| Container child restrictions | Parsys policies | No (flat table model, no containers) | Yes — component-filters restrict children (e.g. only card inside cards) |
| Pre-publish validation | Custom workflow only | Workflow-based — reviewer rejects non-conforming content | No (unless custom built) |
| Authoring-time enforcement | Strong — policies prevent adding wrong components | None — open authoring, governance via review | Moderate — filters limit options in dialogs/containers |
| Governance model | System-enforced (prevent) | Process-based (review and reject) | Hybrid — partial system guardrails + review |
