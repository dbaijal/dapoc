# Governance & Template Enforcement — DA vs JCR (xWalk) Comparison

---

## Use Case: Governance & Template Enforcement

How content governance, template policies, and authoring guardrails are enforced to maintain content consistency and quality across the site.

---

| Dimension | Details |
|---|---|
| **Current TFS State** | AEM 6.4 Editable Templates with full policy system. Template policies restrict which components are allowed per template, which RTE options are available, which styles can be applied, and which content structures are locked. Authors cannot add components that are not permitted by the template policy. Governance is system-enforced at authoring time. |
| **DA Approach** | Governance is achieved through a combination of guidance and process controls. DA Library panel shows the approved set of blocks and page templates — guiding authors on what to use. DA plugins (CTA, Forms, Brightcove, etc.) provide constrained input where needed — dropdown selections, validated fields, and guided authoring dialogs that prevent freeform errors. Page templates in Library provide pre-built page structures as starting points. DA permissions control who can edit which content paths. Request Publish workflow provides a review gate before content goes live — reviewers can reject non-conforming content. This is a process-based governance model with guidance mechanisms. |
| **JCR Approach (AEMaaCS + xWalk)** | Governance is achieved through a combination of system guardrails and authoring constraints. component-definition.json and component-filters.json restrict which child blocks can go inside a container (e.g. only accordion-item inside accordion). Model definitions control which properties appear in the UE dialog per block with constrained field types (required fields, select dropdowns with fixed options). Section filters restrict which blocks are allowed in a section — though these apply site-wide, not per page type. Style options are limited per block via the model's `classes` field. Page templates provide initial page structure. However — there is no equivalent of per-page-type template policies, no locked page regions, and no per-template content policies for RTE options. This is a hybrid governance model with partial system enforcement. |
| **Functional Differences** | Neither DA nor xWalk provides traditional AEM Editable Template + Policy enforcement. Both represent a governance simplification from AEM Sites — neither can restrict which blocks are allowed on a specific page type. DA achieves input governance through plugins that provide constrained dialogs (similar outcome to xWalk model field validation, different mechanism). xWalk achieves input governance through model definitions with field types and component-filters for container children. Both support page templates as starting points (not enforced after creation). Both support bulk metadata for programmatic governance across folder subtrees. The core difference: DA's guardrails are guidance-based (Library, plugins, workflow review). xWalk's guardrails are partially system-enforced (filters limit options in UI, models constrain field values). |
| **Operational Impact** | **DA:** Authors have freedom in what blocks to place on a page but receive guidance through the Library panel and constrained input through plugins. Governance overhead is shared between plugin-based guidance (prevents input errors at authoring time) and reviewer approval (validates overall content conformance before publish). No component-definition or filter maintenance required — governance changes are config/plugin updates. **xWalk:** Authors see limited options in UE dialogs based on component-filters and model definitions — reducing potential for incorrect block placement within containers. Field-level constraints reduce reviewer burden for data quality. However, maintaining component-definitions, filters, and models requires ongoing development effort for every block or governance change across sites. |
| **Governance Impact** | **DA:** Governance operates at two levels: (1) Guidance layer — Library panel, plugins with constrained inputs, page templates as starting points. (2) Enforcement layer — publish approval workflow where reviewers validate content before it goes live. Path-based permissions control who can edit where. Bulk metadata enforces template assignment across folder subtrees. **xWalk:** Governance also operates at two levels: (1) System guardrails — component-filters restrict container children, model definitions constrain field inputs, section filters limit block options in sections. These apply site-wide (not per page type). (2) Review layer — no built-in publish workflow (unless custom built). Path-based permissions control editing access. Inherited page properties enforce metadata across content hierarchy. |
| **Change Mgmt Impact** | **DA:** Shift from policy-enforced governance to guidance + process-based governance. Authors adapt to: using the Library for block/template selection, plugin dialogs for constrained fields, and understanding that publish approval is the quality gate. Training focuses on: approved blocks per page type (documented guidelines), plugin usage, and the approval workflow. **xWalk:** Shift from full template policies to partial system guardrails. Authors adapt to: UE interface with limited block options per container, constrained dialog fields, and understanding that some restrictions exist but not at the page-template level. Training focuses on: new UE interface, which blocks go where (partially system-enforced, partially guidelines-based). |

## Detailed Comparison: Governance Mechanisms

| Governance Aspect | AEM 6.4 (Current TFS) | DA | xWalk (JCR) |
|---|---|---|---|
| Allowed blocks per page template | Template policies — system-enforced per template | No per-page-type restriction — any block on any page | No per-page-type restriction — component-filters restrict container children only, apply site-wide not per template |
| Locked page structure (fixed regions) | Editable Template locked regions | No | No |
| RTE formatting restrictions per template | Content policies restrict formatting options per template | No | No |
| Style restrictions per template | Template policies control which styles appear per template | No per-template restriction | Partial — model `classes` field limits style options per block (applies to all instances of that block, not per template) |
| Block property restrictions | Policies hide/show dialog fields per template | No (unless plugin provides specific fields) | Yes — component-definition controls which fields appear per block (same fields everywhere, not per template) |
| Container child restrictions | Parsys policies | No (flat table model, no containers) | Yes — component-filters restrict children (e.g. only card inside cards) |
| Field input validation (constrained values) | Content policies + dialog field types | Achieved via plugins — dropdown selections, guided dialogs, constrained inputs | Achieved via model definitions — required fields, select dropdowns with fixed options |
| Page templates (initial page structure) | Editable Templates with locked structure | Yes — Library templates provide starting point (not enforced after creation) | Yes — page templates provide starting point (not enforced after creation) |
| Library / palette guidance | Component palette filtered by policy per template | DA Library panel shows approved blocks and templates — soft guidance (same across all pages) | UE block palette shows available blocks from component-definition — soft guidance (same across all pages) |
| Bulk metadata governance | Page properties with inheritance | Yes — bulk metadata spreadsheet enforces values across folder subtrees | Yes — inherited page properties enforce values across content hierarchy |
| Pre-publish validation | Custom workflow only | Built-in — Request Publish workflow, reviewer rejects non-conforming content | No built-in publish workflow (unless custom developed) |
| Authoring-time input constraints | Strong — policies prevent adding wrong components + constrain inputs per template | Partial — plugins provide constrained inputs where implemented | Partial — model definitions constrain inputs for all defined fields |
| Governance model | System-enforced (prevent at authoring time, per template) | Guidance + process-based (Library guidance, plugin constraints, workflow review) | Hybrid — partial system guardrails (container filters, field constraints) + no built-in publish review gate |
