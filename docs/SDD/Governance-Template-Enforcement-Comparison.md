# Governance & Template Enforcement — DA vs JCR (xWalk) Comparison

---

## Use Case: Governance & Template Enforcement

How content governance, template policies, and authoring guardrails are enforced to maintain content consistency and quality across the site.

---

| Dimension | Details |
|---|---|
| **Current TFS State** | AEM 6.4 Editable Templates with full policy system. Template policies restrict which components are allowed per template, which RTE options are available, which styles can be applied, and which content structures are locked. Authors cannot add components that are not permitted by the template policy. Governance is system-enforced at authoring time. |
| **DA Approach** | Governance is achieved through a three-layer model: guidance, validation, and process control. **Guidance layer:** DA Library panel shows the approved set of blocks and page templates — guiding authors on what to use. DA plugins (CTA, Forms, Brightcove, etc.) provide constrained input where needed — dropdown selections, validated fields, and guided authoring dialogs that prevent freeform errors. Page templates in Library provide pre-built page structures as starting points. **Validation layer:** Preflight runs at preview/publish time and validates that page content conforms to governance rules — including expected blocks per template type, required metadata, and content compliance. Preflight blocks preview/publish until the page passes all rules. Preflight plugins can be extended with TFS-specific template rules. **Process layer:** DA permissions control who can edit which content paths. Request Publish workflow provides a review gate before content goes live — reviewers can reject non-conforming content. This is a guidance + validation + process-based governance model where enforcement occurs at preview/publish time rather than authoring time. |
| **JCR Approach (AEMaaCS + xWalk)** | Governance is achieved through a combination of system guardrails and authoring constraints. component-definition.json and component-filters.json restrict which child blocks can go inside a container (e.g. only accordion-item inside accordion). Model definitions control which properties appear in the UE dialog per block with constrained field types (required fields, select dropdowns with fixed options). Section filters restrict which blocks are allowed in a section — though these apply site-wide, not per page type. Style options are limited per block via the model's `classes` field. Page templates provide initial page structure. However — there is no equivalent of per-page-type template policies, no locked page regions, and no per-template content policies for RTE options. Publish from UE is direct — no built-in publish review gate in the EDS xWalk workflow. This is a hybrid governance model with partial system enforcement at authoring time. |
| **Functional Differences** | Neither DA nor xWalk provides traditional AEM Editable Template + Policy enforcement. Both represent a governance simplification from AEM Sites — neither can restrict which blocks are allowed on a specific page type at authoring time. **Key difference in enforcement timing:** In DA, authors can place any block freely during authoring — governance is enforced at preview/publish time via Preflight (non-compliant pages cannot be published). In xWalk, some constraints are enforced at authoring time (component-filters limit container children, model definitions constrain field values) — but these apply site-wide, not per template. DA achieves input governance through plugins that provide constrained dialogs (similar outcome to xWalk model field validation, different mechanism). Both support page templates as starting points (not enforced after creation). Both support bulk metadata for programmatic governance across folder subtrees. The enforcement shift: AEM 6.4 prevents at authoring time → DA detects and blocks at preview/publish time → xWalk partially prevents at authoring time (container children only). |
| **Operational Impact** | **DA:** Authors have freedom in block placement during authoring but receive guidance through the Library panel and constrained input through plugins. Preflight validates governance rules before any content can be previewed or published — non-conforming content is blocked with actionable error messages. This reduces the governance burden on manual reviewers (Preflight catches rule violations automatically; reviewers focus on content quality and brand alignment). Governance rule changes are config/plugin updates — no code deployment required for adding or modifying Preflight rules. **xWalk:** Authors see limited options in UE dialogs based on component-filters and model definitions — reducing potential for incorrect block placement within containers. Field-level constraints reduce reviewer burden for data quality. However, maintaining component-definitions, filters, and models requires ongoing development effort for every block or governance change across sites. No built-in publish review gate means governance relies entirely on authoring-time constraints and manual process. |
| **Governance Impact** | **DA:** Governance operates at three levels: (1) Guidance layer — Library panel, plugins with constrained inputs, page templates as starting points. (2) Validation layer — Preflight enforces governance rules at preview/publish time (blocks per template type, required fields, compliance rules). Pages cannot be published until Preflight passes. (3) Process layer — Request Publish workflow where reviewers validate content quality. Path-based permissions control who can edit where. Bulk metadata applies default values across folder subtrees. **xWalk:** Governance operates at two levels: (1) System guardrails — component-filters restrict container children, model definitions constrain field inputs, section filters limit block options in sections. These apply site-wide (not per page type). (2) Manual process — no built-in publish review gate in EDS xWalk workflow; governance relies on authoring-time constraints plus team process. Path-based permissions control editing access. Inherited page properties apply values across content hierarchy. |
| **Change Mgmt Impact** | **DA:** Shift from policy-enforced governance to guidance + validation + process-based governance. Authors adapt to: using the Library for block/template selection, plugin dialogs for constrained fields, and understanding that Preflight is the quality gate at preview/publish (non-conforming content will be blocked with clear error messages). Training focuses on: approved blocks per page type (documented guidelines), plugin usage, understanding Preflight feedback, and the approval workflow. **xWalk:** Shift from full template policies to partial system guardrails. Authors adapt to: UE interface with limited block options per container, constrained dialog fields, and understanding that some restrictions exist but not at the page-template level. Training focuses on: new UE interface, which blocks go where (partially system-enforced, partially guidelines-based). No publish review workflow means training must emphasize getting it right during authoring. |

## Detailed Comparison: Governance Mechanisms

| Governance Aspect | AEM 6.4 (Current TFS) | DA | xWalk (JCR) |
|---|---|---|---|
| Allowed blocks per page template | Template policies — system-enforced per template | No authoring-time restriction — any block can be placed on any page. Preflight validates expected blocks per template type at preview/publish time (non-compliant pages blocked) | No per-page-type restriction — component-filters restrict container children only, apply site-wide not per template |
| Locked page structure (fixed regions) | Editable Template locked regions | No | No |
| RTE formatting restrictions per template | Content policies restrict formatting options per template | No | No |
| Style restrictions per template | Template policies control which styles appear per template | No per-template restriction | Partial — model `classes` field limits style options per block (applies to all instances of that block, not per template) |
| Block property restrictions | Policies hide/show dialog fields per template | No (unless plugin provides specific fields) | Yes — component-definition controls which fields appear per block (same fields everywhere, not per template) |
| Container child restrictions | Parsys policies | No (flat table model, no containers) | Yes — component-filters restrict children (e.g. only card inside cards) |
| Field input validation (constrained values) | Content policies + dialog field types | Achieved via DA plugins — dropdown selections, guided dialogs, constrained inputs (at authoring time for plugin-based blocks) | Achieved via model definitions — required fields, select dropdowns with fixed options |
| Page templates (initial page structure) | Editable Templates with locked structure | Yes — Library templates provide starting point (not enforced after creation) | Yes — page templates provide starting point (not enforced after creation) |
| Library / palette guidance | Component palette filtered by policy per template | DA Library panel shows approved blocks and templates — soft guidance (same across all pages) | UE block palette shows available blocks from component-definition — soft guidance (same across all pages) |
| Bulk metadata governance | Page properties with inheritance | Yes — bulk metadata spreadsheet applies default values across folder subtrees | Yes — inherited page properties apply values across content hierarchy |
| Pre-publish validation | Not applicable (prevented at authoring time) | Preflight — validates all governance rules before preview/publish. Extensible with custom TFS-specific rules. Blocks publish until page is compliant. | No built-in pre-publish validation in EDS xWalk workflow |
| Authoring-time input constraints | Strong — policies prevent adding wrong components + constrain inputs per template | Partial at authoring time (plugin-based for Forms, CTA, Brightcove) + Full at preview/publish time (Preflight validates all governance rules before content can go live) | Partial — model definitions constrain inputs for defined fields, component-filters restrict container children |
| Governance model | System-enforced (prevent at authoring time, per template) | Guidance + validation + process-based (Library guidance, plugin constraints, Preflight enforcement at preview/publish, workflow review) | Hybrid — partial system guardrails (container filters, field constraints, site-wide) + no built-in publish review gate |
| Enforcement timing | Authoring time (author cannot perform the action) | Preview/publish time (author can perform the action; Preflight detects and blocks before content goes live) | Authoring time for container/field constraints; no enforcement for block selection per page type |
